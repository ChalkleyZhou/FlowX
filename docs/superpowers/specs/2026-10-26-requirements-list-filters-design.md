# 需求列表筛选优化设计

## 背景

需求列表当前把 Codex/Cursor 默认执行器放在筛选栏中，但它只影响后续启动工作流时的偏好，并不决定列表结果。列表同时缺少按发布版本、规划状态和优先级筛选的能力，导致需求池无法快速定位某个版本或推进阶段的需求。

## 目标

- 从需求列表筛选区移除 Codex/Cursor 执行器选择。
- 支持按工作区、项目、发布版本、规划状态和优先级组合筛选。
- 让筛选状态可以通过 URL 保存、刷新和分享。
- 让项目、版本之间保持联动，避免出现无效筛选条件。
- 在筛选无结果时明确告知用户当前存在筛选条件，并提供一键清除。

## 方案

本次只改 Web 端需求列表的本地筛选，不改 API、Prisma 或数据模型。页面继续一次加载需求、工作区和项目数据；筛选条件使用 `URLSearchParams` 作为持久化来源。

筛选参数如下：

| 参数 | 含义 |
| --- | --- |
| `workspaceId` | 工作区 ID |
| `projectId` | 项目 ID |
| `versionId` | 发布版本 ID |
| `planningStatus` | `UNSCHEDULED`、`SCHEDULED`、`IN_PROGRESS` 或 `DONE` |
| `priority` | `URGENT`、`HIGH`、`MEDIUM` 或 `LOW` |

版本选项根据当前工作区和项目联动。未选择项目时，版本选项展示为“项目 · 版本”，避免不同项目存在同名版本时产生歧义；选择项目后只展示该项目的版本。切换工作区会清理不属于该工作区的项目和版本，切换项目会清理不属于该项目的版本。

Codex/Cursor 偏好继续由创建需求、原型导入和启动工作流入口使用，列表筛选区不再修改该偏好。

## 页面行为

- 首次打开页面时从 URL 恢复筛选条件；无效或不存在的参数会被忽略并清理。
- 筛选项发生变化时更新 URL，并保留与打开详情/启动流程相关的其他查询参数。
- 有任一筛选条件时显示“清除筛选”按钮。
- 无筛选条件且列表为空时继续显示“还没有录入任何需求”；有筛选条件但无结果时显示“当前筛选条件下没有需求，请调整筛选或清除条件”。
- 列表项保留项目、规划状态、优先级徽标，并增加发布版本徽标。
- 总数卡片显示全部需求数，当前筛选结果卡片显示筛选后的数量。

## 测试

在 `apps/web/src/pages/RequirementsPage.test.tsx` 增加以下覆盖：

1. 从 URL 恢复工作区、项目、版本、规划状态和优先级筛选。
2. 组合筛选只显示匹配的需求。
3. 切换项目或工作区时清理失效的版本/项目参数。
4. 点击清除筛选后恢复全量列表并清理 URL 参数。
5. 筛选无结果时显示调整筛选提示。
