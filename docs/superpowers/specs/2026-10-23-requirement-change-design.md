# 需求变更最小闭环设计

状态：用户已于 2026-10-23 确认实施。

## 目标与方案选择

需求创建后仍能持续演进。一句话即可提交变更，较大调整可重新走研发流程，不增加任务分配或变更审批。

可选方案：普通评论成本最低，但容易不进入研发上下文；每次变更都重新走流程可追踪，但操作过重。推荐统一的正式变更记录，提供“补充变更”和“重新走流程”两种提交方式。

## 用户操作

需求详情与工作流详情提供同一个“需求变更”入口，填写一段变更说明即可，内容可以只有一句话，例如“导出增加 Excel 格式”。

- **补充变更（默认）**：保存后立即展示在需求和关联工作流中，后续 AI 生成、重新生成和本地任务上下文自动包含变更；继续当前流程。
- **重新走流程**：以现有需求加上变更说明发起新一轮产品澄清、设计、方案和开发流程，沿用原需求、版本及仓库范围；不要求复制新需求，也不要求逐步点回退。

不增加单独的变更确认页，提交按钮即表达用户选择。只做文字变更，本轮不扩展 ZIP 替换、评论回复、人员分配或自动影响分析。

## 内容与流程规则

变更记录不可静默覆盖，记录提交人、提交时间、原文、提交方式与关联流程。需求详情按时间展示，较长历史折叠。

原有 PRD、设计和方案保留；补充变更作为正式增量，与原内容共同构成最新要求。已确认文档不被后台直接改写，后续生成读取增量时需明确以最新变更为准，并保留仍未解决的冲突。

为需求记录递增修订号；每次云端生成或本地领取保存读取的修订号。旧任务不会被伪装成已接收新变更，工作流展示“有新变更，当前任务尚未同步”。运行中的本地任务需结束或重新领取才能获取新上下文。

选择重新走流程时创建关联的新一轮流程，保留旧流程及产物历史，并明确新旧轮次关系。新流程必须使用变更后的需求上下文，不能因旧需求已完成构思或导入设计而自动跳过需要重做的阶段。

同一仓库仍有活跃任务时，先保存变更记录，明确提示需结束旧任务后再接续新一轮；不自动终止 IDE 或并行启动冲突流程。记录保留“待启动”状态及重试入口；重新提交或重试不得重复创建流程。

其他需求仅排队待执行、没有实际运行阶段或本地会话时，不阻塞本需求重新走流程，也不被作废。仓库准备前后都复查实际任务，避免准备期间的新领取导致冲突。

旧轮若仅待执行或待确认、没有运行中的云端阶段和本地会话，可以标记为被本次变更替代并接续新轮，保留产物与历史，不要求用户删除旧流程。被替代的轮次应明确展示原因。

本轮提供新变更与未同步状态展示，不新增跨阶段的审批门禁，也不声称运行中的 IDE 已经自动接收变更。

## 实现边界与验证

独立保存需求变更记录及其流程关联，沿用现有组织权限、工作流创建服务和云端/本地上下文入口。API、Web 类型与端云读取方同步更新；不将全部变更简单拼接进用户原始描述字段。

验证至少覆盖：一句话提交、空内容拒绝、跨组织隔离、时间顺序与刷新恢复；后续 AI 与本地任务包含变更、旧任务显示未同步；重新走流程保留历史且不复用过时的已确认产物；活跃任务冲突、启动失败可恢复、并发及重试不重复建流程。

交付时同步 README、用户手册及 Web 镜像、系统设计和 CHANGELOG，运行相关测试与全仓检查，并用本地浏览器验证两条路径。
