# 工作流接续与端云多人协同优化方案

状态：用户已于 2026-10-22 确认实施。目标：让产品、设计、研发和测试能够围绕同一条需求接续工作，并明确本地执行与平台状态的边界。

## 已确认的依据

- 本地实测需求已有活跃工作流，详情页却只有「启动研发工作流」；API 已返回关联工作流与仓库，无需另建关联模型。
- 工作流首屏将统计、需求全文和禁用的质量操作置于当前阶段之前，产品用户难以判断当前要做什么。
- 本地构思、设计、Spec & Plan 已使用 ExecutionSession，现有页面仅对开发阶段显示详细执行会话。顶部使用 StageExecution.RUNNING 推断「后台执行」，无法表达本地是否仍在回报。
- 构思、设计、Spec & Plan 的领取方法遇到已有会话会直接复用；真实 `claimLocalDesign` 配合合成只读 fixture 已确认用户 B 会拿到 A 的会话，未提示冲突。回传方法检查组织与终态，但尚未统一核对回传人是否为领取人。
- 本地当前位置查询只按流程状态返回 `generate` 等动作，没有读取当前领取人；必须在生成前提示占用，不能只在最后回传时拒绝。
- 冒烟已有数据库唯一租约、分端领取、追加原始结果和失败优先聚合；其回传入口目前只传组织上下文，未传用户身份。
- 无报告时，真实 Service/Controller 返回 HTTP 200 空响应；前端 JSON 解析失败，详情 Promise.all 整体失败并误报「提测不存在」。隔离实验已复现，见本地验证记录。

## 方案选择

选择复用现有模型、补齐任务与交接信息。相比只修文案，此方案覆盖实际接续与写入归属；相比全面重做工作台，不新增重复的任务状态机，能直接利用现有流程与权限。

## 一、需求作为接续入口

需求详情展示关联工作流的当前业务状态、仓库范围和进入入口。存在一条活跃流时，主操作为「继续工作流」；存在多条时，逐条展示并选择，不能静默替用户选一个。已完成与失败流程可查看历史，不得被误作仍在本地执行。

「另起工作流」保留为次级操作，并沿用需求列表已有的启动选择能力；显示当前占用范围，后端继续校验冲突，不把多仓并行一律禁用。避免需求详情绕过项目、版本和仓库选择直接创建默认流程。

## 二、当前任务与端云交接前置

工作流标题后直接显示当前任务：当前阶段、待执行/待回传/待人工确认、当前执行人、执行位置、本地最近回报、下一步动作与确认后去向。任务状态取服务器当前阶段，不随用户查看历史阶段而改变。阶段导航、当前产物和操作优先；需求背景、分支和质量入口作为辅助内容。

读取会话必须是纯读取，不能调用会隐式领取的 handoff 接口来渲染状态。复用 ExecutionSession 与现有健康度计算，不新增前后端各自推断的状态机。

本地状态必须区分：已领取但未收到真实本地回报、最近收到回报、长时间无回报、等待平台确认、失败/取消。领取时间不得被解释为本地进程已成功启动；旧会话无明确回报证据时显示「尚未确认本地运行状态」。无回报不能自动视为已停止或允许他人覆盖。

有明确领取人时显示其姓名；缺少记录时显示「未记录执行人」，不能假称「待我」。平台已确认收到产物后显示待评审，不能仍提示用户继续本地生成。保留真实错误和重新加载入口，后台刷新保留已有内容、避免重叠请求，终态停止不必要轮询。

## 三、多人领取与回传边界

同一阶段只允许一个有效执行会话。同一领取人重复领取复用原会话；其他人领取应返回可理解的冲突，显示已有执行人及查看当前流程的路径。并发首次领取也必须保证只生成一份有效会话，使用现有事务、阶段状态和幂等键防重，并把竞争冲突转成可恢复的业务错误。

本地当前位置查询附带当前执行人的展示信息、会话引用与状态；已被其他人领取时返回现有兼容动作 `none` 和「等待当前执行人回传」说明，不向旧客户端发出可生成指令。新客户端仍从服务端取得动作，不能再按本机文件或聊天上下文推断。上游产物作为上下文，不转移其阶段的执行归属。

构思、设计、Spec & Plan 和冒烟回传统一核对组织和领取人。其他团队成员可以查看进展、评审已回传产物，但不能以别人的会话提交结果、变更本地运行状态或冒充执行人。相同执行人的幂等重试继续有效。旧会话缺少领取人时，不自动分配给打开页面的人；回传应提示「历史会话未记录执行人，需要确认停止并重新交接」，不能继续使用组织级权限替代领取身份。

开发阶段沿用现有停止请求与本地回执。构思、设计、方案的旧执行器尚无完整协作式停止回执，增加显式「结束本次本地任务并重新交接」：仅原执行人或组织管理员可操作，必须确认已在原设备停止任务并填写原因。平台明确说明这只终止平台会话，不能远程关闭 IDE。事务同时将旧会话置为取消、当前阶段尝试置为失败并记录操作人/原因；之后其他人才能领取新尝试。旧会话晚到回传必须被拒绝。无领取人的历史会话仅允许同组织管理员走这条恢复路径。失联本身不触发释放。

冒烟保留按目标端/用例租约并行、原始结果不覆盖、失败优先聚合、版本指纹校验与有效租约阻止归档的规则。页面显示目标端、执行人、领取范围、租约是否仍有效及回传结论，避免只展示原始英文状态。

## 四、验收入口可靠性

明确无报告返回 JSON null 的 HTTP 契约，并覆盖真实响应，而不仅 mock Service 返回值。无报告是正常状态，不是提测不存在。

提测基本信息先独立呈现；报告或轮次失败时保留可用信息并分别提供重试。主请求失败显示加载失败与恢复操作，不能依据 request 为空推断记录不存在。真正的 404/403 与网络错误应可区分，避免泄露无权限记录的详情。

## 验收场景

1. 需求已有一条或多条活跃流程，用户可以直接进入正确流程，不意外启动重复任务；没有活跃流程时仍能正常启动。
2. 打开工作流首屏即可知道当前要交付/确认什么；查看历史阶段不会改变当前任务摘要。
3. 用户 A 在本机领取构思/设计/方案，用户 B 看得到 A 的进展与回传状态，但无法复用 A 的领取凭据写入结果；A 可安全重试。
4. 两人同时领取同一阶段，仅一个成功，另一人得到可恢复冲突；互不重叠的工作流与冒烟目标仍可并行。
5. 本地未启动、失联、等待同步与已回传待确认可区分；失联不会自动变成已停止。
6. 冒烟的多人租约竞争、重复回传、越权回传、旧版本结果、失败优先和未完成归档门禁均有测试证据。
7. 无报告的提测详情可正常显示；报告或轮次失败不清空基本信息；主请求失败可重试，不误报不存在。
8. 浏览器验证需求接续、工作流首屏和质量详情；API/Web 必要测试与构建通过，手册及镜像同步。
9. 本地当前位置查询在别人执行时不指示生成；明确结束旧任务后，另一人可以领取新尝试，旧会话无法再覆盖新产物。

## 验证范围与交付要求

实施前补充会失败的回归测试，再进行最小实现；端云和多人边界用真实数据库或 HTTP 边界验证关键竞态与契约。正常业务数据不用于制造竞争或覆盖实验。

本地 UI 仅有旧设计流程，完整 AI 新生成质量、真实 IDE 启动与跨设备多人接续需要专用体验需求和可用执行环境。交付时分别报告已实现、已验证与外部环境未覆盖事项，不以单元测试代替跨设备实测。

2026-10-22 实施前基线：`workflow-local-design`、`workflow-local-spec-plan`、`workflow-local-execution`、`local-smoke.service` 和 `execution-control.integration` 共 5 个文件、45 项测试通过。该结果不覆盖上述其他领取人复用会话的场景；实施时需先增加对应失败回归测试。

不包含：全面工作台重构、新增排期/消息系统、产品验收矩阵重建、无回执强制接管。它们可作为后续优化，但不能用其替代本轮的接续、状态、归属与可靠性工作。
