# 提测 AI 范围与人员分派设计

## 状态

已完成产品设计确认，进入实现计划阶段。

## 1. 背景与问题

当前测试流程把用例库和模块选择放在测试设计阶段，把候选逐条处理放在测试设计页面，再在执行轮次中重新选择用例和执行人。用户需要在多个页面重复确认相同范围，提测后的关键工作无法围绕真实代码变更快速展开。

本次调整把提测作为测试范围的主入口：创建提测草稿后自动分析需求、技术方案、研发提交和代码库上下文，结合已有用例库生成第一版范围。测试人员只需删除不满意的库、模块或用例，补充缺口并确认整体范围，然后按模块分派执行人。

## 2. 目标

1. 创建提测后自动生成一版可执行的测试范围草稿。
2. AI 同时复用/优化已有用例，并在库中缺少覆盖时生成新用例候选。
3. 采用默认纳入、人工删改的交互，不要求逐条点击接受或排除。
4. 支持用例库、模块、批量和单条用例删除或补充，快速收敛范围。
5. 支持模块默认负责人、模块内多人拆分和单条用例改派。
6. 通过确认版本和用例快照保证后续执行、报告和历史追溯稳定。
7. AI 生成的新用例不自动写入正式用例库，是否沉淀由人工单独决定。

## 3. 非目标

- 不在本期建设长期固定的冒烟套件管理。
- 不要求测试人员逐条审核 AI 候选。
- 不让 AI 自动修改正式用例库或覆盖已有用例版本。
- 不改变已有测试轮次结果、Bug 回归和本地执行租约语义。
- 不把页面操作复制成独立的网页解析流程供本地 Agent 使用。

## 4. 用户流程

```text
创建提测草稿
  -> 自动启动 AI 范围分析
  -> 输出默认纳入的范围草稿
  -> 人工删减、补充、编辑
  -> 确认范围并生成确认版本/快照
  -> 按模块设置默认负责人并分派
  -> 单条用例必要时改派或拆分给多人
  -> 完成分派
  -> 创建功能测试或回归轮次
```

页面使用“确认范围”和“完成分派”两个整体确认动作。产品文案不再使用“冻结范围”作为用户操作名称；服务端仍保留不可变快照，确保确认后的执行事实不受长期用例库变化影响。

## 5. AI 范围分析

### 5.1 输入

AI 分析由提测创建动作自动触发，输入范围由服务端根据提测关联关系组装：

- 需求标题、描述、验收标准、风险与影响、功能模块和需求变更记录；
- 已确认的设计方案和 `Spec & Plan`；
- 关联研发工作流的提交记录、代码差异、仓库和分支信息；
- 当前项目用例库与 Workspace 共享用例库的有效用例、模块层级、版本和适用端；
- 当前提测的项目、发布版本、需求和工作流范围。

服务端负责权限、项目边界和来源快照校验，AI 不直接访问数据库或绕过 API 读取用例库。

### 5.2 输出

分析结果以范围草稿形式返回。每条候选保留来源、版本、模块、生成类型、匹配理由、覆盖目标和完整用例内容。生成类型沿用现有语义：

- `REUSE`：复用已有用例；
- `OPTIMIZE`：按本次变更生成调整后的用例内容；
- `CREATE`：用例库没有覆盖，生成当前提测专用新用例；
- `EXCLUDE`：AI 识别到相似但不适用于本次变更的候选，作为分析说明保留，不进入默认范围。

`REUSE`、`OPTIMIZE` 和 `CREATE` 默认进入范围草稿。用户不满意时可以删除；AI 的来源和理由默认折叠展示，不把它们变成逐条决策门槛。

### 5.3 重试与版本

首次分析失败时，提测保留草稿和可用的已有数据，页面显示可公开的失败原因并提供重试。重试生成新的分析草稿版本；已经确认的版本不被覆盖。需求、技术方案或研发交付发生变化时，后续可将当前确认版本标记为需要重新分析，但本期不自动替用户重做已确认范围。

## 6. 页面交互

### 6.1 顶部状态区

提测详情顶部展示需求、版本、关联工作流、代码范围、AI 分析状态和数量摘要。对用户只展示以下主状态：

- `分析中`；
- `待确认范围`；
- `待分派`；
- `执行中`；
- `已完成`。

数量摘要至少包含范围用例数、模块数、未分派数和 AI 生成新用例数。

### 6.2 范围工作台

范围工作台采用“穿梭框操作习惯”，但以模块树和批量操作为核心：

- 左侧展示可搜索的用例库/模块树，库级和模块级均可加入或移除；节点显示有效用例数；
- 中间展示当前 AI 草稿，按用例库和模块分组，支持全组选择、批量删除、查看详情和编辑；
- 右侧展示本次最终范围摘要，按库/模块汇总，支持搜索、批量移除和补充已有库用例；
- 新生成用例和已有用例使用统一列表结构，差异只通过来源标签说明；
- 只有“确认范围并进入分派”会推进流程，不出现逐条接受、逐条拒绝或逐条确认按钮。

删除操作支持用例库、模块、批量和单条四个粒度。删除只是从本次提测草稿移除，不删除长期用例库数据。

### 6.3 分派工作台

范围确认后展示分派工作台：

- 每行一个模块，展示用例总数、已分派数、模块默认负责人和执行进度；
- 设置模块负责人后，该模块未单独指定执行人的用例继承该负责人；
- 模块可拆给多人，展开模块后支持批量选择用例并改派；
- 单条用例可以覆盖模块默认负责人；
- 提供“仅看未分派”“仅看我负责”“按人员汇总”快捷视图；
- 未分派用例数量持续显示，未完成分派时禁止进入可执行轮次。

### 6.4 新用例沉淀

`CREATE` 候选默认只写入本次提测确认快照。用户可以在用例详情中主动选择“保存到项目用例库”，保存前可编辑标题、模块、步骤、预期、优先级和标签。保存动作复用现有用例创建/编辑权限、编号分配和版本规则；失败不影响本次提测快照。

### 6.5 操作状态与错误

- 首次加载展示局部 loading，已有草稿时后台刷新不清空当前内容；
- 分析失败保留已有范围，明确区分分析失败、权限不足、来源不存在和网络错误；
- 范围或分派保存失败保留用户未提交的编辑，允许重试；
- 发生并发修订冲突时重新读取最新版本，提示用户选择保留当前草稿或刷新后继续；
- AI 返回缺失字段、越权来源或无法映射模块时，拒绝该批结果并保留上一版草稿，记录可定位的错误分类。

## 7. 数据与 API 设计

### 7.1 复用现有模型的边界

`TestRequest` 继续作为提测聚合根，`TestPlan` 保存本次计划，`TestCaseSnapshot` 保存确认后的不可变快照。现有 `TestDesign`/`TestDesignCandidate` 可作为 AI 分析的内部草稿和来源记录，但页面主入口从独立测试设计页迁移到提测详情。

长期用例仍由 `TestCaseDefinition` 管理。AI 新用例在用户主动保存前不得创建 `TestCaseDefinition`。

### 7.2 新增或调整的接口能力

具体路径在实施计划中确定，接口需要覆盖以下能力：

1. 创建提测后启动并查询 AI 范围分析状态；
2. 分页读取范围草稿，按库、模块、来源类型和关键词筛选；
3. 批量移除、补充已有用例、编辑草稿用例和重试分析；
4. 以 `scopeRevision` 做乐观并发校验，确认范围并生成快照；
5. 分页读取模块分派摘要和用例分派明细；
6. 按模块批量设置默认负责人，按用例覆盖负责人，完成分派；
7. 从 `CREATE` 快照主动保存到项目用例库。

写接口必须复用现有 Workspace/项目权限、成员状态校验、幂等和审计规则。批量接口只接受显式 ID 集合，不能把当前分页结果推断为完整范围。

### 7.3 快照与执行

确认范围时，在事务内把当前草稿转换为 `TestCaseSnapshot`，写入来源定义、来源版本、完整步骤/预期、`origin`、`selectedBy` 和范围确认版本。分派记录指向快照用例；创建测试轮次时从已分派快照生成 `TestRunCase`，不再要求用户重新选择同一批用例。

如果用户需要重新分析，服务端创建新的草稿修订；已有确认版本、已创建轮次和执行结果保持不变。

## 8. 本地 Agent 适配结论

本次结论：**需要适配**。

影响入口包括现有 `flowx_create_test_design`、`flowx_generate_test_design`、`flowx_get_test_design`、`flowx_update_test_selection`、`flowx_add_test_candidates`、`flowx_test_requests`、`flowx_create_test_run` 以及 `flowx-local-test` Skill。原因是提测主入口、默认纳入语义、确认时机和分派数据都会变化，本地 Agent 不能继续按“逐候选处理后再显式确认测试设计”的旧顺序解释新流程。

实施时应优先复用现有 API 业务服务和 MCP 注册入口，扩展动作和可选字段，保持旧客户端对旧测试设计流程的兼容。新服务端对旧客户端请求必须保持明确的旧行为；新版工具遇到不支持的范围草稿或分派能力时返回可识别错误，不静默忽略字段。

需要同步更新：

- `packages/flowx-local/src/mcp.ts` 的工具 schema、请求映射、返回解析和错误说明；
- `packages/flowx-local/templates/flowx-local-test/SKILL.md` 及 `flowx-continue`/`flowx-intake-requirement` 中的提测顺序；
- `docs/local-agent-guide.md` 的提测和测试任务说明；
- `@flowx-ai/protocol` 中新增的状态、分派和分页契约（如实施确定跨包共享）。

本地 Agent 仍通过 MCP/API 获取范围和快照，不解析 Web DOM，不直连数据库；人员分派仍由服务端校验组织成员和权限。

## 9. 测试与验收

### 后端

- 提测创建自动触发分析，重复请求不创建重复草稿；
- AI 输入来源的 Workspace、项目、需求、工作流和代码范围校验；
- `REUSE`、`OPTIMIZE`、`CREATE` 默认纳入，删除后不进入快照；
- 新用例未主动保存时不创建 `TestCaseDefinition`，主动保存成功后正确分配编号；
- 范围确认的事务、`scopeRevision` 冲突和快照不可变性；
- 模块默认负责人、模块内多人拆分、单条覆盖和未分派门禁；
- 重试、失败保留旧草稿、已确认版本不被覆盖；
- 跨 Workspace/项目、非活动成员和无权限写入均被拒绝；
- 旧提测、旧测试设计、本地旧客户端请求保持兼容或返回明确升级错误。

### Web

- 提测创建后分析中、分析完成、失败和重试状态；
- 用例库/模块批量加入、删除、搜索和分页后选择保持；
- AI 草稿默认纳入，不出现逐条确认操作；
- 范围确认后才能进入分派，分派完成后才能创建轮次；
- 模块默认分派、多人拆分、单条改派、未分派筛选和统计；
- 新用例主动保存对话框及失败恢复；
- 并发修订、网络失败和空范围提示；
- 详情页原有快照、轮次、报告、缺陷和分页数据不回归。

### 本地包与文档

- MCP 工具发现、输入 schema、API 路径/方法/字段和失败映射；
- `flowx-local-test` Skill 的新调用顺序和“默认纳入、人工删改、整体确认”语义；
- `@flowx-ai/protocol` 测试和构建（若新增共享契约）；
- `docs/user-manual.md` 与 `apps/web/public/user-manual.md` 同步；
- `docs/local-agent-guide.md` 与 `apps/web/public/local-agent-guide.md` 同步。

## 10. 分期边界

本期先实现提测详情中的 AI 范围草稿、批量删改、整体确认和人员分派。AI 自动重新分析的高级版本管理、基于历史执行结果的智能优先级、拖拽式分派和自动化脚本生成不属于本期；若来源变化需要重新分析，先提供显式重试并保留已确认版本。
