# 多仓分支交付最小闭环

状态：用户已确认按本方案实施。沿用共享 PRD、设计与方案，不引入任务分配、负责人调度、依赖图或必须领取的子任务。

## 用户路径

方案确认后，成员自行在本地开发。在工作流开发阶段选择已有仓库、填写已推送的分支；平台核验并记录完整 commit、提交人、时间。其他成员可以独立提交其他仓库或同仓库的其他分支。提交分支不意味着整个需求完成。

开发阶段显示本次尝试的分支清单。同仓库可由多人提交不同分支，最终每个仓库选择一条代表本次交付的分支，避免没有明确集成版本就进入提测。成员确认选中版本和未覆盖仓库的提示后，统一进入既有 AI 审查与人工评审，随后沿用提测流程。平台不代替 Git 合并，不宣称已联调或测试通过；首版仅接收分支名，PR/MR URL 解析与 CI 状态连接留待后续。

## 数据与接口

- 增加 `CodeBranchSubmission`，关联工作流、开发阶段 attempt、工作流仓库、提交人，保存 branch 和服务端取得的完整 headSha。同一人同一尝试重复提交同仓同分支更新为新 SHA，不能替换其他人的记录。
- `GET /workflow-runs/:id/code-delivery` 返回仓库、当前尝试提交、是否可提交、不可提交原因及当前已冻结交付。
- `POST /workflow-runs/:id/code-delivery/branches` 接收 `{ workflowRepositoryId, branch }`，无需执行会话。首次提交以 `executor: CODE_DELIVERY` 创建开发 attempt 并进入 `EXECUTION_RUNNING`，后续提交共用该 attempt。
- `POST /workflow-runs/:id/code-delivery/confirm` 接收 `{ submissions: [{ id, headSha }], confirmed: true }`。只接受当前 attempt、去重且至少一条的显式选择；确认前重新获取分支，移动过的分支要求重新提交。缺少仓库展示提醒，不强制所有仓库都有变更。
- 所有接口校验登录与组织、仓库属于本工作流；提交与确认使用工作流版本 CAS，外部 Git I/O 在事务外完成，事务内再次检查版本及当前阶段。不接受跨流程、旧 attempt 或前端过期 SHA。

## 审查与提测衔接

平台在隔离临时 Git 仓库读取所选分支的实际 diff，并冻结分支 headSha、baseSha、提交人和仓库。将真实 diff 转成既有 CodeExecution/开发阶段输出，原工作流状态机推进到 REVIEW_PENDING。没有差异、分支不可读或版本改变时不推进，不创建伪造审查结果。多分支以各自相对基线的差异展示，不声称已合并。

冻结交付保存至阶段输出及工作流级 `GIT_COMMIT` Artifact 元数据，使既有冒烟版本指纹绑定所选 commit；不为分支交付创建虚构的执行会话或证据。确认后不能静默修改，返工或回退进入新 attempt，旧记录保留查看。

现有单人本地/云端执行链路保持兼容。活动的旧执行与分支汇集互斥，需走其原停止/取消流程，不能在任务仍运行时直接确认交付。前端将分支交付作为默认开发入口，旧执行方式保留为辅助入口。

## 验收

1. 两个成员可各自提交分支；无任务分配或执行会话前置要求，提交不会跳到审查。
2. 重复提交更新本人记录；跨组织、外部仓库和过期阶段均拒绝。
3. 确认展示选中仓库/分支/SHA及未覆盖仓库，读取真实 diff 后才推进，冻结版本进入既有质量链路。
4. 分支移动、无差异、Git 失败或并发状态变化不会误推进；旧尝试不混入新交付。
5. Web 覆盖加载、错误恢复、提交、选择确认、路由迟到；真实 SQLite/本地 Git 验证多人、并发与状态衔接。
