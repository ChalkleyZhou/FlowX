# 测试与质量模块体验与本地执行闭环设计

日期：2026-11-04。状态：用户已确认设计方向和完整功能测试、缺陷回归及冒烟兼容范围；尚未实施，不替代当前运行规则。

## 1. 目标与边界

本次围绕两件事展开：优化平台交互，让用户知道当前进展和下一步；打通根据需求选择用例库、确定用例、在本地执行、回传执行记录、输出测试报告的完整链路。

用户已确认本地执行范围：完整功能测试与缺陷回归，兼容现有冒烟。方案复用现有本地 Agent、执行会话与 Artifact 能力。不同测试框架由本地工具执行；本期不建设通用测试调度集群、脚本托管平台、传统提测审批或跨项目质量大屏。

这里的“本地执行用例库”应落到具体对象：从指定用例库选择本次需求相关用例，冻结为测试计划快照，再执行这些快照。用例库不是一次执行任务，库内后续编辑不能改写历史结果。

## 2. 现有能力与实际断点

以下结论来自代码和文档静态核对，未进行浏览器实测或本地端到端执行。

| 环节 | 已有能力 | 需要补齐的体验或联动 |
| --- | --- | --- |
| 需求关联 | 测试设计关联需求、版本、工作流；工作流详情提供生成用例和提测入口 | 当前创建提测主要围绕已完成工作流填写；需求详情缺少直接进入质量链路的入口 |
| 用例资产 | Workspace 共享库、项目库、模块、导入、编辑、版本、覆盖关系 | 库管理与本次选例缺少衔接，无法在生成测试设计时明确限定用例库 |
| AI 选例 | 生成复用、优化、新增、不纳入建议，人工确认后入库 | 当前按更新时间各取项目库、共享库最多 250 条，不能把这种候选读取当作完整检索；缺少检索范围和遗漏提示 |
| 确认范围 | 已有测试设计确认、快照、范围检查与过期检测 | 用户需在工作流、测试设计、提测多个页面之间切换；缺少连续的下一步引导 |
| 本地执行 | 冒烟支持目标端、领取租约、代码版本核对、证据上传、批量回传 | 这套会话能力目前限定于 `LOCAL_SMOKE` 和 `SMOKE` 快照，未覆盖正式功能测试与回归 |
| 普通执行 | 后端支持初测、Bug 回归及逐例结果 | 当前提测详情只拉取本地冒烟轮次；执行记录列表没有轮次详情跳转，难以查看和处理完整结果 |
| 覆盖矩阵 | 冒烟能按目标端生成用例矩阵 | 当前把所选冒烟快照复制到每个目标端，尚未表达某条用例只适用于 Web 或 API 等情况 |
| 报告 | 冒烟通过门禁后生成版本化 HTML Artifact，可下载 | 目前是提测前的冒烟报告，门禁失败时不能通过该入口生成报告，也不汇总正式功能测试和回归 |

主要核对位置：

- `apps/web/src/pages/quality/QualityDialogs.tsx`：创建提测和关联测试设计。
- `apps/web/src/pages/quality/QualityRequestDetailPage.tsx`：冒烟详情、手动刷新与下载。
- `apps/web/src/pages/quality/QualityRunsPage.tsx`：执行记录列表。
- `apps/api/src/quality/test-designs.service.ts`：用例候选读取及人工确认。
- `apps/api/src/quality/test-requests.service.ts`：关联校验与快照创建。
- `apps/api/src/quality/test-runs.service.ts`：普通初测和 Bug 回归。
- `apps/api/src/quality/local-smoke.service.ts`：本地冒烟领取、回传、汇总和门禁。
- `packages/flowx-local/src/mcp.ts`、`packages/flowx-local/templates/flowx-local-smoke/SKILL.md`：已有本地入口及操作说明。

## 3. 可选路径

| 路径 | 优点 | 局限 | 建议 |
| --- | --- | --- | --- |
| 以测试任务详情串起全链路，扩展现有本地执行能力 | 保留已有数据模型和入口，既解决操作割裂，也补齐功能测试与报告 | 需要同步 Web、API、本地包和协议 | 推荐 |
| 先只调整现有页面布局和按钮 | 范围小，短期可改善易用性 | 普通用例仍不能复用本地领取回传，最终测试报告仍缺失 | 只能作为交付中的第一部分 |
| 重建独立测试执行与调度平台 | 可统一脚本、设备与远程执行 | 范围大，与现有会话和 Artifact 能力重复 | 本次不采用 |

## 4. 推荐的用户操作主线

```text
选择项目、版本与需求
    ↓
选择用例库及模块 → AI 推荐相关用例 → 人工补选、排除、确认覆盖
    ↓
冻结本次测试范围
    ↓
创建执行轮次：冒烟 / 功能初测 / 缺陷回归
    ↓
确认目标端、测试环境和代码版本 → 在本地执行
    ↓
逐例回传结果与证据 → 平台持续展示进度
    ↓
生成本轮报告 → 失败项修复后新建回归轮次 → 生成任务汇总报告
```

测试设计仍可从 Spec & Plan 确认后提前准备，与开发并行。正式提测和执行继续校验研发完成及测试范围就绪；入口前移不意味着放宽现有门禁。

### 4.1 入口和平台布局

保留现有“提测管理、用例库、执行记录”导航和路由。将提测详情作为贯穿全流程的工作页面，面向用户说明其承担一次测试任务的组织与跟踪职责。暂不增加独立报告中心。

- 需求详情提供“测试与质量”入口，带入项目、版本和需求；优先进入已有测试设计或提测，避免重复创建。
- 发起提测改成连续步骤：关联需求 → 确认测试范围 → 设置执行。工作流由需求带出，只展示用户需要确认的可用版本和完成状态。
- 测试设计未确认、已过期、已关联提测等情况，展示具体原因和可点击的修复入口。
- 详情采用“概览、测试范围、执行轮次、缺陷与回归、测试报告”页签。标题区域固定展示状态、阻塞原因和当前主要操作。
- 已有数据时后台刷新保持内容、筛选和滚动位置；运行期间安静更新，结束后停止轮询。加载失败保留上次数据并显示更新时间和重试入口。

主要操作随进展变化：待准备范围时“选择测试用例”，范围待确认时“确认测试范围”，可执行时“创建执行轮次”，执行中“查看执行进度”，执行结束后“查看测试报告”。按钮不可用时说明缺少什么以及去哪里补齐。

### 4.2 从需求选择用例库，再确定具体用例

选例页面采用“左侧库和模块、中间用例列表、右侧当前范围摘要”。支持项目库和有权限的 Workspace 共享库多选，记录实际选择范围。

- 默认推荐当前项目库；共享库是否纳入由用户明确确认。
- 支持按模块、优先级、标签、目标端筛选，手工选择与 AI 推荐并存。
- AI 按需求、验收标准、实际改动和已有覆盖关系推荐用例，展示推荐理由、覆盖点和风险。
- 列表默认展示标题、来源、优先级、覆盖需求及处理状态；步骤、数据和预期结果在侧栏查看。优化候选支持对照原用例查看差异。
- 支持批量纳入复用用例、批量排除；修改正式用例必须单独明确确认，不能把“本次纳入”隐含成“修改共享库”。
- 未找到合适用例时可补充本次用例；是否沉淀为正式库资产由用户确认。已有已确认设计保持原有语义。
- 展示每条需求的验收点与选中用例对应关系，以及未覆盖项。覆盖结论必须有可核对的依据。

检索应先在所选库中筛选和匹配，再控制 AI 上下文数量。候选总量、实际检索和送入 AI 的数量要有记录；达到限额时明确告知并允许缩小范围或继续检索，不能静默漏掉较早的关键用例。

确认后冻结用例版本、测试数据、步骤、预期结果、选择理由和适用端。执行的是冻结内容；需求或代码基线变化后提示重新评估，已发生的执行与旧报告继续保留。

### 4.3 本地执行

执行轮次统一表达“测什么、在哪测、谁在测、测到哪里”。冒烟、功能初测和缺陷回归使用同一套领取、会话、证据与回传基础能力，同时保留各自的业务前置条件。

创建轮次时确认范围、目标端、环境和代码基线。按用例适用端生成矩阵；未配置适用端时要求确认，不直接把所有用例乘以所有目标端。

平台提供“在本地执行”，连接已有本地服务和 IDE 启动能力。展示设备连接、仓库匹配、版本核对和任务领取的结果；未安装、未登录、缺少仓库映射或版本不匹配时给出对应操作。启动 IDE 成功只表示任务已交接，实际开始执行以服务端会话和进度记录为准。

本地 Agent 也应能通过 MCP 查询当前用户可执行的任务和待测用例，再领取指定目标端及范围，不要求用户复制内部 ID。复用已有任务发现能力时，需验证质量任务确实包含在结果中。

用例定义中的步骤属于测试说明，不等于自动化脚本。首期支持 Agent 调用现有测试命令、浏览器或其他工具执行，以及人工辅助完成后回传。没有执行条件的用例应报告阻塞或跳过及原因，不能因为“生成了脚本”就标记通过。

执行过程中支持逐批保存已完成用例和进度；任务完成时再汇总会话。租约续期、释放、取消和晚到结果必须由服务端校验。页面区分“执行中、回传中、回传失败、结果已过期”，并能看到最后活动时间。

### 4.4 执行记录、证据和缺陷回归

执行记录列表可进入轮次详情，展示关联需求、测试类型、执行人、设备、环境、代码版本、开始时间、耗时和逐例结果。默认突出失败、阻塞、待执行和待回传项。

逐例明细至少包含：用例快照及版本、预期与实际结果、结论、执行人、执行时间、环境、代码版本、耗时、日志/截图/视频 Artifact、缺陷关联。证据通过有权限的预览或下载入口展示，不只列内部 ID。

回传采用稳定幂等键，重复提交不重复创建结果；已上传的证据必须可访问且属于当前任务允许的范围。回传失败支持重试，并明确服务端是否已接受。

失败项可以关联已有 Bug 或显式创建 Bug。修复完成后创建新的回归轮次，默认选择对应失败项和必要的关联用例。保留初测失败与回归通过两份事实，不覆盖初测记录。更换代码版本后明确回归验证范围，不能把旧版本通过项直接算成新版本已验证。

### 4.5 测试报告

必须区分三个概念：提测前冒烟门禁是否满足、一次执行轮次的实际结论、整个需求/版本测试任务的汇总结论。

报告生成独立于通过门禁：失败和阻塞时也可以输出报告。未全部执行时允许输出带明显“阶段报告/未完成”标识的报告；正式结束本轮时明确剩余未测项和原因，不把未测算通过。关闭前若仍有有效领取，需等待结束或显式取消并由服务端拒绝晚到结果。

提供本轮报告和任务汇总报告，包含：

1. 项目、版本、需求、测试范围、目标环境与代码基线。
2. 总用例数、适用的用例与目标端组合数、已执行/未执行数、通过/失败/阻塞/跳过数。
3. 执行完成率与通过率的计算口径。建议完成率为已记录终态结果数除以应测组合数；通过率为通过数除以应测组合数，单列阻塞和跳过，避免隐藏未完成覆盖。
4. 需求验收点覆盖、未覆盖内容和排除原因。
5. 失败项、关联缺陷、修复与回归过程、尚存风险。
6. 逐例结果、证据链接、执行人、设备、环境和实际代码版本。
7. 报告生成时间、版本、数据截止点与引用的执行轮次。

报告保存为不可变的 Artifact；后续结果变化生成新版本。任务汇总显式选择纳入轮次和代码基线，区分历史已通过与当前基线有效验证，不直接对所有历史结果取最后一次值。自动化统计决定事实结论，AI 只补充解释和风险摘要。保留 HTML 在线查看与下载，PDF 等格式后续按需求增加。

## 5. 数据、状态与端云适配

继续复用 `TestDesign → TestRequest → TestPlan → TestCaseSnapshot → TestRun → TestExecution → TestExecutionCaseResult` 和 Artifact，避免新建与现有执行会话重复的体系。

需要补齐的契约包括：选定的库/模块和检索信息、用例适用端、功能测试与回归的本地领取和回传、分批进度、执行控制，以及报告种类和汇总基线。具体字段、接口、迁移职责及验证安排见实施计划的“目标契约”和各任务。

保持状态职责清晰：测试设计状态说明范围是否可用；提测状态说明整体准备和测试结论；轮次状态说明本轮是否结束；执行会话状态说明某次本地工作和回传情况。报告生成不直接把任一对象改成通过。多轮并行时由统一聚合规则计算任务结论，避免一个轮次结束就覆盖其他轮次的状态。

| 边界 | 本地适配结论 | 工作内容 |
| --- | --- | --- |
| Web 页面与导航 | 不适用（纯展示部分） | 复用现有 API 数据，优化连续操作、错误恢复和结果查看 |
| 需求选例、测试范围、API | 需要适配 | API 提供相同选例范围、权限和快照规则，本地消费者也能读取 |
| 本地领取、执行与回传 | 需要适配 | 扩展现有冒烟能力承接功能与回归；API 负责业务约束，本地保持薄桥接 |
| Artifact 上传与预览 | 复用现有能力 | 复用 `flowx_upload_artifact` 和 Artifact 服务，补齐质量会话关联及权限验证 |
| MCP、CLI、Skill/Adapter | 需要适配 | 先评估扩展既有工具；确需新增时补工具发现、任务获取、执行说明和实际参数透传 |
| `@flowx-ai/protocol` | 需要适配 | 共享执行结果、进度和控制契约，同步运行时校验及消费者 |

兼容策略：保留既有 `flowx_create_smoke_run`、`flowx_list_smoke_tasks`、`flowx_claim_smoke_task`、`flowx_submit_smoke_report` 和对应 API 的冒烟语义；旧 Skill 继续只做冒烟，不自动扩大执行范围。新能力通过增量契约和明确的版本/能力识别暴露。服务端不支持时返回可识别的不支持原因；本地版本不足时提示升级并重新加载 MCP。历史快照和报告保持原样，不推算补造执行事实。

## 6. 建议交付顺序与验收

以同一条闭环分三步交付；前两步交付说明必须明确完整报告或完整本地执行尚未支持的范围。

| 步骤 | 交付重点 | 可核对的验收结果 |
| --- | --- | --- |
| 1. 平台交互与选例 | 需求入口、连续步骤、统一详情、库/模块选择、人工补选和覆盖检查 | 用户能从需求找到现有任务，明确本次库和具体用例；遇到缺少设计或版本过期能在页面完成补齐 |
| 2. 通用本地执行 | 功能/冒烟/回归统一会话能力、任务发现、进度、证据、可靠回传 | 本地通过正式工具领取功能用例，真实执行并逐例回传；Web 可查看结果与证据，重试不重复写入 |
| 3. 报告与回归闭环 | 轮次报告、任务报告、失败出报告、修复回归和版本留存 | 初测失败也能生成报告；修复后产生独立回归记录，汇总报告能同时追溯初测、修复、回归及当前基线 |

必要验证覆盖：

- 主路径：需求 → 指定库选例 → 确认快照 → 本地领取与执行 → 证据上传 → 回传 → 报告 → 回归。
- 交互：空状态、缺少前置材料、生成失败重试、权限不足、保留数据的刷新、轮询停止和页面切换后的旧响应隔离。
- 契约：MCP 工具发现、输入 schema、实际请求透传、API 校验、返回消费，不能只运行类型检查。
- 一致性：范围和代码版本过期、跨项目访问、领取冲突、租约过期、取消后晚到结果、重复回传、多轮并行及旧客户端兼容。
- 报告：失败/阻塞/跳过/未执行均可如实呈现，统计可复算，证据可访问，历史版本不被覆盖。

代码落地时按受影响范围运行 API、Web、local、protocol 测试与构建，以及全仓 `pnpm check`。用户文档需要同步 `README.md`、`docs/quality-foundation.md`、`docs/user-manual.md`、`docs/local-agent-guide.md` 及手册镜像，工具描述和发布 Skill 与实际支持范围一致。

本设计确认后进入实施规划；在代码交付之前，使用手册继续描述当前已实现能力。实施计划见 `docs/superpowers/plans/2026-11-04-quality-execution.md`。
