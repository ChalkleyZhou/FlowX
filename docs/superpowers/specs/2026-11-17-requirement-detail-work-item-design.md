# 需求详情页工作项化重构设计

## 背景

需求、问题和缺陷已经统一为 `WorkItem`，但 Web 端仍存在多套详情体验：`RequirementDetailPage` 承载需求修改、排期和研发流程，`IssueDetailPage` 与 `BugDetailPage` 各自维护编辑表单，`WorkItemDetailPage` 又提供了一套较简化的统一入口。继续只优化需求页面会把共享字段和操作继续分叉。

当前 `/work-items/:id` 路由实际使用 `WorkItemDetailPage`；`RequirementDetailPage` 保留着需求专属流程测试和历史实现。本次先优化该统一入口中的需求展示，同时以统一工作项壳层作为设计基线。问题和缺陷页面本轮保持现有页面布局，但共享组件和 API 契约必须可供后续迁移使用。

## 目标与范围

### 目标

1. 打开需求详情后先阅读需求内容，辅助信息不抢占首要阅读路径。
2. 将版本工作台的需求修改项带入需求详情页，并同时提供摘要和完整记录入口。
3. 在详情页直接编辑负责人、优先级和发布版本，交互与版本工作台保持一致。
4. 让需求、问题、缺陷共享同一套工作项级字段、编辑能力和详情页布局边界。

### 本次范围

- 重排 `/work-items/:id` 对需求类型的详情信息架构，主要修改 `WorkItemDetailPage`。
- 新增需求详情右侧的工作项快速编辑区。
- 新增需求修改项摘要区，复用现有需求修改 API 和状态语义。
- 扩展需求更新 API 支持 `ownerUserId`，并校验组织归属。
- 抽取或新增可复用的工作项元信息、编辑和摘要组件边界。
- 保留需求现有的工作流、执行计划、原型导入、排期和完整修改记录能力。

### 不在本次范围

- 不重排 `IssueDetailPage` 和 `BugDetailPage` 的页面布局。
- 不为问题和缺陷新增需求修改项能力。
- 不新增 MCP、CLI、Skill 或 `@flowx-ai/protocol` 入口。
- 不改变工作项状态机、工作流推进规则和排期业务规则。

## 信息架构

页面按“需求内容优先，辅助信息可见，流程信息可追溯”组织。

### 顶部标题区

显示标题、需求编号、项目、规划状态、优先级和发布版本。操作区保留返回列表、准备测试、排期、编辑内容、删除、继续当前工作流、启动研发工作流等现有动作；根据数据状态显示适用动作。

### 两列主区域

桌面端使用 `lg:grid-cols-[minmax(0,1fr)_360px]`，窄屏变为单列并将右栏移动到主栏后方。

左侧主栏展示需求正文，顺序固定为：

1. 需求描述
2. 验收标准
3. 功能模块
4. 风险&影响
5. 产品需求文档
6. 备注

空值显示“未填写”；产品需求文档继续识别 HTTP URL 并提供新窗口打开能力。

右侧辅助栏包含三个紧凑区块：

- **工作项信息**：负责人、优先级、发布版本；只读状态下显示当前值，点击“编辑”后切换为 `PagedSelect`/`Select`，支持保存和取消。
- **需求修改摘要**：展示最近 3 条 `RequirementChange`，包括版本号、修改人、时间、模式和重启状态；提供“查看全部修改”和“提交需求变更”。
- **排期摘要**：展示规划状态、总预估人天和排期成员数量；提供“查看完整排期”。规划状态仍由完整排期区编辑。

### 推进与历史区

两列区域之后按以下顺序展示：原型导入（存在时）、当前工作流、执行计划、历史工作流、完整需求修改记录、完整人员排期。完整区块保留现有分页、轮询、重试和状态语义。

## 组件设计

### `WorkItemMetaPanel`

共享工作项元信息展示和编辑边界，接收当前 `WorkItem`/`Requirement`、项目和工作区上下文，以及 `onSaved` 回调。需求页只启用负责人、优先级和版本；后续问题/缺陷迁移时可扩展状态、严重级别等字段。

保存统一调用 `api.updateWorkItem` 工作项更新契约，避免在页面中复制成员查询、版本查询和组织权限逻辑。保留并扩展 `api.updateRequirement` 是为了兼容需求专属旧组件和现有测试；后续问题/缺陷迁移时以 `updateWorkItem` 为唯一快速编辑入口。

### `RequirementChangesSummary`

只读摘要组件，调用 `api.getRequirementChanges(requirementId, undefined, { page: 1, pageSize: 3 })`。摘要加载失败时只影响右栏摘要，并提供重试；完整 `RequirementChangesPanel` 继续负责提交补充变更、重新走流程、原型 ZIP、轮询和跳转。

### 需求正文编辑

保留 `RequirementEditDialog` 作为完整内容编辑入口，负责标题、描述、验收标准、功能模块、风险影响、产品需求文档和备注。快速编辑区不与长文本编辑混用。

### 共享壳层边界

共享壳层只负责标题区、工作项元信息、来源/执行摘要和通用操作布局；需求、问题、缺陷通过 `kind` 决定专属内容。需求专属区域包括验收标准、需求修改项、原型导入和排期；问题和缺陷后续迁移时保留各自处理结论、复现上下文和修复工作流。

## API 与数据流

### 需求更新

扩展 `UpdateRequirementDto`、`RequirementsService.update` 和 Web `api.updateRequirement` 的 payload：

```ts
ownerUserId?: string | null;
```

传入非空用户 ID 时，服务端校验用户属于当前项目工作区对应的组织；传入 `null` 时清空负责人。返回值继续包含 `ownerUser`，使前端保存后可以立即更新显示。

快速编辑保存一次提交三个字段当前值，成功后将响应合并到页面状态并提示“需求信息已更新”；失败时保留草稿和错误信息，不覆盖已展示内容。需求更新不改变需求修改记录，只有“提交需求变更”才创建 `RequirementChange`。

### 竞态与刷新

详情页继续使用现有 `requestVersion` 防止迟到请求覆盖新需求。快速编辑保存后触发静默详情刷新，不能将页面重新切换到整页 loading。修改摘要和完整修改记录沿用现有 silent refresh、分页和后台轮询规则。

## 错误与权限

- 负责人不属于当前组织时，API 返回可定位的校验错误，前端保留选择状态并显示错误。
- 保存发生 `updatedAt` 冲突时，提示刷新后重试；不自动覆盖他人修改。
- 修改摘要失败不阻塞需求正文和工作流区域。
- 权限仍由现有认证上下文、Controller guard 和 Service 校验控制，前端不新增绕过路径。
- 不在错误信息中返回 token、完整凭据或个人登录态。

## 验证计划

### Web

- 详情首屏按需求内容优先的顺序渲染，窄屏右栏下移。
- 快速编辑可加载、保存、取消负责人/优先级/版本；清空负责人和清空版本均可用。
- 保存失败保留草稿和错误；保存成功只更新详情数据，不清空现有区块。
- 修改摘要展示最近记录、空状态、加载失败和重试入口；完整修改面板原有提交/重启行为回归。
- 需求现有工作流选择、历史工作流、原型导入、测试准备、排期和删除测试继续通过。

### API

- `ownerUserId` DTO 接受合法 ID 和 `null`，拒绝非字符串值。
- 服务校验组织归属，正确更新和清空 `ownerUserId`，返回 `ownerUser`。
- 需求更新不意外改变 `RequirementChange`、工作流或排期关联。
- 既有需求更新、工作流、权限和删除测试回归。

### 本地工具适配结论

本次变化是 Web 详情布局和需求更新 API 契约增强。`flowx-local`、FlowX MCP、CLI、Skill/Adapter 和 `@flowx-ai/protocol` 没有新增入口，也不需要直接适配；本地 Agent 继续通过已有工作项 API/MCP 消费负责人、版本和流程状态。后续若把问题/缺陷专属编辑能力开放给本地 Agent，再单独评估协议和工具 schema。
