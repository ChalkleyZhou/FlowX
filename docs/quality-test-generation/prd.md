# 需求驱动的测试用例生成与确认

## 背景与问题

FlowX 已有测试与质量中心，能够维护 Workspace 共享用例、项目用例、提测范围、执行轮次和 Bug 回归。但测试用例目前主要在提测阶段由人工维护或由外部 AI 选取，尚未充分利用研发工作流中已经确认的产品需求、设计方案和 Spec & Plan。

这带来几个问题：

- 测试人员需要重复理解需求和设计，再手动整理测试范围。
- 新需求生成的用例可能与现有用例重复，或遗漏对现有用例的修订。
- 用例库会持续累积相似、过时或覆盖边界不完整的用例。
- 冒烟用例缺少针对本次改动的明确生成依据，容易退化成一套长期不变的固定清单。
- 用例准备与开发执行无法自然并行，提测时才发现用例未准备完成。

## 目标用户

- 测试/QA：审查生成的测试范围，决定复用、优化或新增哪些用例，并确认本次冒烟范围。
- 产品经理：确认关键业务场景、验收标准和风险边界已被测试覆盖。
- 研发人员：在开发期间查看即将用于提测和验收的测试范围，提前发现实现遗漏。
- 项目负责人：在提测前确认测试设计已经完成，而不是在测试执行后补齐。

## 目标

1. 在 PRD、设计方案和 Spec & Plan 已确认后，允许生成本次需求的测试用例候选。
2. 用例生成与开发执行可以并行，不互相阻塞。
3. 生成结果必须与当前项目用例库和 Workspace 共享用例库比对，避免无意义的重复用例。
4. 对每个候选给出复用现有用例、优化现有用例、新增用例或不纳入的明确建议。
5. 根据本次改动动态生成冒烟用例，不维护长期固定的历史冒烟用例库。
6. 提测前必须完成测试用例与冒烟用例的人工确认。
7. 保留用例版本、确认记录和提测快照，保证历史执行结果可追溯。

## 非目标

- 不自动执行浏览器、接口、移动端或设备测试。
- 不在本阶段建设自动化测试脚本生成。
- 不建设长期固定的项目冒烟套件。
- 不让 AI 未经确认直接修改正式用例库。
- 不替代测试人员对高风险业务、合规和线下流程的专业判断。
- 不改变 Bug 回归已有的独立执行轮次语义。

## 用户故事与核心场景

### 场景一：在开发期间准备测试用例

作为测试人员，我希望在 Spec & Plan 确认后立即生成测试用例，以便在研发执行期间并行审查测试范围，而不必等到开发完成后再开始准备。

### 场景二：复用已有用例

作为测试人员，我希望系统展示与本次需求覆盖目标相同或高度相似的现有用例，并解释匹配原因，以便直接复用而不是重复创建。

### 场景三：优化已有用例

作为测试人员，我希望系统指出现有用例与新需求之间的差异，并给出优化后的完整内容和前后差异，以便确认后更新现有用例版本。

### 场景四：补充缺失用例

作为测试人员，我希望系统基于产品规则、交互设计、异常路径和实现风险识别覆盖空白，并生成可编辑的新用例候选。

### 场景五：生成本次冒烟用例

作为测试人员，我希望系统只根据本次改动和受影响的关键链路生成精简冒烟用例，以便快速判断构建是否具备继续测试的条件。

### 场景六：发起提测

作为研发或测试人员，我希望系统在发起提测时检查测试用例和冒烟用例是否已经确认；未确认、已过期或存在未处理候选时，不能进入可测试状态。

## 产品流程

```text
PRD 确认
  -> 设计确认
  -> Spec & Plan 确认
  -> 创建测试设计草稿
  -> AI 读取本次变更范围并比对现有用例库
  -> 输出覆盖分析、复用/优化/新增候选和本次冒烟用例
  -> 测试人员逐项处理并确认
  -> 开发工作流完成
  -> 提测门禁校验
  -> 冻结本次提测用例快照
  -> 创建冒烟或完整测试执行轮次
```

用例生成和开发执行可以并行。两者只在提测门禁处汇合：开发工作流必须完成，测试设计也必须确认。

## 生成输入

每次生成应使用以下已确认内容：

- PRD 中的目标、非目标、用户故事、产品规则、边界情况和验收标准。
- 设计文档及设计稿中可观察的页面、流程、状态和交互。
- Spec & Plan 中的实现范围、影响点、风险和验证要求。
- 当前需求、项目版本、关联工作流和仓库范围。
- 当前项目用例库和 Workspace 共享用例库中的有效用例。
- 开发执行已经产生时，可补充使用本次实际变更摘要；实际变更与已确认 Spec & Plan 不一致时，应提示重新生成或补充分析。

## 生成结果

一次测试设计至少包含以下内容：

1. 覆盖摘要：本次变更涉及的功能点、角色、主流程、异常路径、权限、数据和兼容性边界。
2. 复用用例：可以原样纳入本次测试范围的现有用例。
3. 优化用例：已有覆盖但内容需要修订的现有用例，必须展示修改原因和前后差异。
4. 新增用例：现有库没有充分覆盖的测试场景。
5. 不纳入建议：相似但不适用于本次变更的用例，并说明排除原因。
6. 冒烟用例：针对本次改动生成的最小关键验证集。
7. 未覆盖项：AI 无法可靠形成用例、需要人工补充判断的风险或场景。

## 产品规则与边界情况

### 生成时机

- 只有 PRD、设计和 Spec & Plan 均已确认，才允许开始正式生成。
- 用例生成不阻塞开发执行，开发人员可以同时进入执行阶段。
- 用户可以在开发执行期间重新生成，但每次重新生成都形成新的草稿修订。

### 现有用例比对

- 比对范围同时包含当前项目库和当前 Workspace 的共享库。
- 当前项目库中的直接匹配优先于 Workspace 共享库中的相似匹配。
- 比对必须同时考虑覆盖目标、前置条件、步骤、预期结果和适用范围，不能只按标题判断。
- 同一候选只能有一个最终处理结果：复用、优化、新增或不纳入。
- 低置信度匹配必须提示人工判断，不得自动归类为复用或优化。

### 用例优化与版本

- AI 只能生成优化建议，不能直接覆盖正式用例。
- 测试人员确认优化后，现有用例版本递增；历史提测快照和执行结果不变。
- 测试人员可以编辑 AI 建议后再确认。
- 若现有用例同时被其他未完成测试设计建议修改，应提示冲突并要求重新比对最新版本。
- 新增的正式功能用例在确认后进入指定的项目库或 Workspace 共享库；默认进入当前项目库。

### 冒烟用例

- 冒烟用例每次根据本次改动动态生成，不依赖或维护历史冒烟套件。
- 冒烟用例应覆盖最关键的正向主链路、系统可用性以及本次改动可能阻断后续测试的风险点。
- 冒烟用例保持数量精简，不等同于把全部 P0/P1 用例复制一遍。
- 冒烟用例只进入本次测试计划快照，不写入长期用例库。
- 测试人员可以编辑、增加、删除或排序冒烟用例。
- 若本次改动确实没有适合的冒烟场景，必须由确认人选择“无冒烟用例”并填写原因，不能由系统静默生成空结果。

### 结果确认

- 确认前，所有复用、优化、新增和不纳入候选必须有明确处理结果。
- 所有未覆盖项必须被补充用例、接受风险或标记为不适用。
- 冒烟用例必须确认，或明确确认本次无冒烟场景。
- 确认操作记录确认人、确认时间、生成修订和来源版本。
- PRD、设计或 Spec & Plan 在确认后发生修订时，已确认测试设计立即标记为“已过期”，必须重新生成或人工确认差异后形成新修订。
- 开发执行的实际变更超出 Spec & Plan 时，提测前必须刷新影响分析。

### 提测门禁

提测进入 `READY` 前必须同时满足：

1. 所有关联研发工作流已完成。
2. 存在已确认且未过期的测试设计修订。
3. 至少存在一个已确认的功能测试用例；特殊情况需明确记录无功能用例原因并经人工确认。
4. 存在已确认的冒烟用例，或存在经人工确认的“无冒烟用例”说明。
5. 所有结构化覆盖检查均已通过，或未通过项已记录接受风险和负责人。
6. 正式用例库更新与本次提测快照冻结已经完成。

门禁不通过时，提测保持草稿状态并列出缺失项，不产生“拒绝”状态。

## 验收标准

1. 用户可以在 Spec & Plan 确认后启动测试用例生成，同时继续开发执行。
2. 生成结果能分别展示复用、优化、新增、不纳入和冒烟用例。
3. 每条复用或优化建议都能定位到现有用例及版本，并展示匹配理由。
4. 优化建议可查看前后差异，确认后现有用例版本递增，历史快照不变。
5. 新增功能用例确认后进入指定用例库；冒烟用例不会写入长期用例库。
6. PRD、设计、Spec & Plan 或实际变更范围更新后，旧确认结果会被标记为过期。
7. 未确认测试设计或冒烟结果时，系统不允许提测进入 `READY`。
8. 测试设计确认且研发工作流完成后，系统能够冻结功能用例和冒烟用例快照并进入提测流程。
9. 系统完整记录生成、编辑、确认、过期和入库动作，能够追溯到操作人与来源版本。

## 仍开放的产品问题

- “接受风险”是否需要测试负责人以外的角色再次确认，可在权限体系明确后决定。
- 实际代码变更与 Spec & Plan 偏差达到什么程度时必须自动使测试设计过期，需要在积累真实项目数据后设定阈值。
- 后续是否将已确认的功能用例直接生成自动化脚本，不属于本期范围。
